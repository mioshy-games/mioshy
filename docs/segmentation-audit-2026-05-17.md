# Segmentation Audit — Mioshy ↔ Brevo

**Date:** 2026-05-17
**Author:** Audit pass (read-only)
**Goal:** Map what exists in the Mioshy codebase before designing a user segmentation system synced to Brevo.

This is a discovery document. No code was changed. Every claim below references a file path; SQL is quoted verbatim from migrations.

---

## TL;DR

The codebase is in a much better position than a greenfield Brevo build would be. Cardcom billing, three-pillar product taxonomy (`subscriptions.product`), couple membership, leads-with-consent, and a working Brevo transactional client are **all already in place**. The gaps are concentrated in three places:

1. **`profiles` has no marketing/language/Brevo columns** — segmentation today would have to derive language from URL geo-detection per-request and there is no user-level marketing consent.
2. **Brevo integration is transactional-only** — no contacts/lists/segments API is wired. There is no place that pushes a contact into Brevo on signup or on purchase.
3. **No unsubscribe surface** — neither a `/unsubscribe` route, an unsubscribe token, nor an unsubscribe footer in templates. This must be built before any marketing send.

The `leads` table is the cleanest existing model for consent-tracked contacts. It already has `marketing_consent`, `terms_accepted`, `terms_accepted_at`, `language`, `country_code`, and an optional `user_id` FK back to `auth.users`. The segmentation system can reuse that consent contract and extend it to authenticated users.

## 1. ✅ What exists and works (ready to use as-is)

### Supabase Auth + profile trigger
- `lib/supabase/{client,server,admin,middleware}.ts` are the canonical clients. `middleware.ts` calls `updateSession()` on every request.
- A Postgres trigger `on_auth_user_created` calls `handle_new_user()` to insert a `profiles` row with `role='user'` whenever `auth.users` gets a new row (`supabase/migrations/002_profiles_auth_hardening.sql`). This is the right place to hook any Brevo contact-create side effect once a server-side worker model is chosen — though the trigger itself runs inside Postgres and shouldn't call HTTP. The right pattern is: trigger writes a sync row; an outbound worker reads it.

### Three-pillar product taxonomy
- `subscriptions.product text NOT NULL CHECK (product IN ('games','journey','adults'))` (`032_subscription_product_pillar.sql`).
- One active subscription per `(user_id, product)` is enforced by `subscriptions_user_product_active_key`.
- This means "subscriber of pillar X" is a clean SQL query today and maps directly to Brevo list membership.

### Couple model with role and pair code
- `couples`, `couple_members(role IN ('owner','partner'))`, `couple_invitations` (`029_between_us_section.sql`, `030_couple_invitations.sql`).
- One active couple per user is enforced (`couple_members_user_id_active_key`).
- Couples cap at 2 (UNIQUE on `couple_invitations(couple_id) WHERE status='accepted'`).
- Segmenting "owner without partner", "owner with partner", "partner" is a join away.

### Invitation tokens (Journey partner)
- `couple_invitations` stores 43-char base64url tokens generated by PG RPC `generate_invitation_token()` from `gen_random_bytes(32)`.
- 30-day hard expiry. Resend rotates the token, extends expiry, bumps `send_count`. Accept is via SECURITY DEFINER RPC `accept_couple_invitations` that adds the partner to `couple_members` and flips status to `accepted`.
- This is **production-grade** and does not need rework for segmentation. Brevo segments can mirror invite state.

### Leads table with consent + GDPR audit
- `leads` already captures `email`, `full_name`, `language ('he'|'en')`, `device_id`, `status ('new'|'converted'|'invalid')`, `country_code`, `vat_rate_percent`, **`marketing_consent`**, **`terms_accepted`**, **`terms_accepted_at`**, and optional `user_id` FK (`012`, `013`, `017`, `018`).
- Unique `(email, device_id)` lets us upsert without dupes.
- Public can INSERT only under tight RLS (`status='new'`, email/device length checks, language whitelist).

### Cardcom billing — payment events as truth source
- `lib/cardcom.ts` + `app/api/billing/cardcom/indicator/route.ts` is the server-to-server webhook. On success it upserts `subscriptions` (subscription path) or inserts `couple_entitlements` (one-time path), stores an encrypted reusable token in `customer_payment_methods`, and creates an invoice.
- Renewal cron: `app/api/billing/renewals/run/route.ts` runs daily, decrypts tokens, calls `ChargeToken.aspx`, handles `failed_attempts → past_due → grace_until → blocked`.
- These are the right hooks for "purchase made", "renewal succeeded", "renewal failed", "subscription blocked" Brevo events.

### Brevo transactional client
- `lib/email/brevo.ts` (102 lines) is a clean wrapper around `POST https://api.brevo.com/v3/smtp/email`. Auth header `api-key` from `BREVO_API_KEY` is already set in `.env.local`.
- Two production templates already use it: `lib/email/templates/couple-invite.ts` (called from `app/actions/couple-invitations.ts:177`) and `lib/email/templates/journey-unlock.ts` (called from `lib/journey-content/notify-unlocks.ts:404`).
- Supports `tags`, `params`, `replyTo`. Tags are already being used (e.g. `["couple-invite","locale:en"]`) which means tag-based Brevo segmentation could start tomorrow on transactional traffic.

### Language detection logic
- `middleware.ts` `detectLocale()` uses a clean hierarchy: URL prefix → `x-vercel-ip-country=IL` → `Accept-Language` → fallback `he`. The resolved locale is stamped on the request as `x-mioshy-locale`.
- This is the right place to capture a "preferred_language at signup" value into `profiles` if/when we add that column.

### Admin leads view
- `app/dashboard/leads/page.tsx` already lists leads by status/language. It's a usable starting surface for "contacts that aren't users yet" once segmentation is added.

## 2. ⚠️ What exists but needs modification

### `profiles` is too thin for segmentation
Today the schema is:

```sql
id uuid PRIMARY KEY REFERENCES auth.users(id),
created_at timestamptz DEFAULT now(),
role text DEFAULT 'user',          -- 'user'|'admin'
full_name text,
mobile text,
phone text,
spins_used integer DEFAULT 0,
last_spin_reset timestamptz
```

It is missing every column that a segmentation worker would care about: language preference, marketing consent, Brevo contact id, last-sync timestamp. See §4 below.

### Signup flow drops consent on the floor
- `components/auth/SignupForm.tsx` collects `fullName, email, phone, password` only.
- `app/actions/auth-actions.ts → signupAction()` (lines 49–110) writes to `auth.users` + `profiles` and that's it. No `marketing_consent`, no `terms_accepted`, no email send.
- The same user, if they filled the `/api/leads/upsert` form before signing up, **already gave consent** in the `leads` row keyed by `(email, device_id)`. We should backfill from there at signup time.

### `subscriptions.stripe_subscription_id` is legacy noise
- Defined in `012_leads_and_subscriptions.sql` but never populated. It signals "Stripe was once considered". Harmless, but a Brevo sync layer should ignore it.

### Brevo client is one-way (send only)
- `lib/email/brevo.ts` only hits `/v3/smtp/email`. There is no call to `/v3/contacts`, `/v3/contacts/lists`, `/v3/contacts/segments`, `/v3/contacts/import`. Marketing segmentation needs a second module that wraps the contacts API.
- `BREVO_SENDER_EMAIL` is referenced in `brevo.ts:7` but **not present in `.env.local`** — a bug today; the call would 400 in dev if no `fromEmail` is passed explicitly. Worth fixing while adding the contacts client.
- `BREVO_LIST_ID` (or `BREVO_LIST_IDS`) is never referenced — it needs to be introduced.

### Lead → user conversion is implicit
- `leads.user_id uuid REFERENCES auth.users(id)` exists (`018_leads_consent.sql`).
- `/api/leads/upsert` re-derives `user_id` from the session cookie and stores it if the visitor is logged in (lines 75–83), but there is no migration / backfill path that takes a pre-existing `leads` row at signup time and stamps `user_id` on it. New signups whose email matches a prior anonymous lead are not linked.
- Status `'converted'` exists on `leads` but is set by a separate RPC in migration `012`, not at signup.

### Admin leads view hides consent fields
- `app/dashboard/leads/page.tsx` line 36–40 selects `id, email, name, language, device_id, status, created_at` — but not `marketing_consent`, `terms_accepted`, `terms_accepted_at`, `country_code`. Once segmentation is live, the admin needs to see "did this person opt-in?" without running SQL.

### `subscription_charges`, `billing_failures`, journey grace columns are unused by any outbound notifier
- Billing failures land in `billing_failures` (`048_billing_failures.sql`) and `subscriptions.failed_attempts` ticks up — but no Brevo event fires. That is a missed dunning campaign trigger.
- The `journey_grace_until` / `journey_blocked_at` columns transition the user's state but nothing emails them. Same for `subscriptions.grace_until`.

## 4. 🔧 Recommended schema changes

These are **proposed** SQL — review before running. Naming follows existing migration conventions.

### 4.1 Extend `profiles` for segmentation

```sql
-- 082_profiles_segmentation.sql
ALTER TABLE public.profiles
  ADD COLUMN IF NOT EXISTS preferred_language    text
    CHECK (preferred_language IS NULL OR preferred_language IN ('he','en')),
  ADD COLUMN IF NOT EXISTS marketing_consent     boolean NOT NULL DEFAULT false,
  ADD COLUMN IF NOT EXISTS marketing_consent_at  timestamptz,
  ADD COLUMN IF NOT EXISTS consent_source        text,
  ADD COLUMN IF NOT EXISTS consent_ip            inet,
  ADD COLUMN IF NOT EXISTS unsubscribed_at       timestamptz,
  ADD COLUMN IF NOT EXISTS brevo_contact_id      bigint,
  ADD COLUMN IF NOT EXISTS brevo_synced_at       timestamptz,
  ADD COLUMN IF NOT EXISTS brevo_sync_error      text;

CREATE UNIQUE INDEX IF NOT EXISTS profiles_brevo_contact_id_key
  ON public.profiles (brevo_contact_id)
  WHERE brevo_contact_id IS NOT NULL;

CREATE INDEX IF NOT EXISTS profiles_marketing_consent_idx
  ON public.profiles (marketing_consent)
  WHERE marketing_consent = true AND unsubscribed_at IS NULL;
```

### 4.2 Mirror Brevo fields on `leads`

```sql
ALTER TABLE public.leads
  ADD COLUMN IF NOT EXISTS marketing_consent_at  timestamptz,
  ADD COLUMN IF NOT EXISTS consent_source        text,
  ADD COLUMN IF NOT EXISTS consent_ip            inet,
  ADD COLUMN IF NOT EXISTS unsubscribed_at       timestamptz,
  ADD COLUMN IF NOT EXISTS brevo_contact_id      bigint,
  ADD COLUMN IF NOT EXISTS brevo_synced_at       timestamptz,
  ADD COLUMN IF NOT EXISTS brevo_sync_error      text;

CREATE UNIQUE INDEX IF NOT EXISTS leads_brevo_contact_id_key
  ON public.leads (brevo_contact_id)
  WHERE brevo_contact_id IS NOT NULL;
```

### 4.3 Outbox table for Brevo sync

```sql
CREATE TABLE IF NOT EXISTS public.brevo_sync_queue (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  contact_kind    text NOT NULL CHECK (contact_kind IN ('profile','lead')),
  contact_id      uuid NOT NULL,           -- profiles.id or leads.id
  email           text NOT NULL,
  reason          text NOT NULL,           -- 'signup'|'consent_change'|'purchase'|'unsubscribe'|'attribute_change'
  payload         jsonb NOT NULL,          -- snapshot of attributes at enqueue time
  status          text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending','in_progress','done','failed')),
  attempts        integer NOT NULL DEFAULT 0,
  last_error      text,
  enqueued_at     timestamptz NOT NULL DEFAULT now(),
  processed_at    timestamptz
);

CREATE INDEX brevo_sync_queue_pending_idx
  ON public.brevo_sync_queue (enqueued_at)
  WHERE status IN ('pending','failed') AND attempts < 5;
```

### 4.4 Unsubscribe tokens

```sql
CREATE TABLE IF NOT EXISTS public.email_unsubscribe_tokens (
  token         text PRIMARY KEY,           -- base64url, generated like couple_invitations
  email         text NOT NULL,
  user_id       uuid REFERENCES auth.users(id) ON DELETE SET NULL,
  lead_id       uuid REFERENCES public.leads(id) ON DELETE SET NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  used_at       timestamptz
);

CREATE INDEX email_unsubscribe_tokens_email_idx
  ON public.email_unsubscribe_tokens (email);
```

### 4.5 Trigger: enqueue sync on relevant changes

(Conceptual — exact triggers TBD based on workflow.)

```sql
-- After INSERT on profiles → enqueue 'signup'
-- After UPDATE of marketing_consent on profiles → enqueue 'consent_change'
-- After INSERT/UPDATE on subscriptions → enqueue 'purchase' or 'attribute_change'
-- After INSERT on couple_members → enqueue 'attribute_change' (partner state changed)
```

## 6. ❓ Open questions (need decision before build)

1. **Contact model in Brevo: profile vs. couple.** Brevo's primitive is an individual contact identified by email. A couple is two contacts. Do we want:
   - (a) each user is a Brevo contact, and the couple is encoded as attributes (`couple_id`, `couple_role`, `partner_email`, `partner_present`)?
   - (b) only the couple owner gets a Brevo contact and the partner is suppressed until they verify?
   - I recommend (a) — Brevo segments need both members reachable for journey campaigns. Confirm.

2. **Where does consent live for authenticated users — `profiles` or a separate `user_consents` table?** A single boolean works for v1. A separate table is cleaner if you ever want a consent history (e.g. "they unsubscribed in March, opted back in in May"). The migration in §4.1 takes the single-row approach; flag if you'd prefer the audit-log approach instead.

3. **Lead → user backfill semantics.** If a visitor opts in on `/api/leads/upsert` with `(email_X, device_A)` and later signs up with `email_X`:
   - Do we copy `marketing_consent=true` from the lead row to `profiles`? (Probably yes.)
   - Do we set `leads.status='converted'` and `leads.user_id=profiles.id`? (Probably yes.)
   - What if multiple `leads` rows match by email (e.g., different devices)? Pick latest by `created_at`? Merge? Confirm.

4. **Brevo segment topology.** Likely lists: `mioshy-all-he`, `mioshy-all-en`, `journey-trial`, `journey-active`, `journey-blocked`, `adults-buyers`, `games-subscribers`, `lead-only`, `partner-pending`. Confirm the seed list before building the sync attribute mapper.

5. **Cardcom indicator → Brevo event emission point.** Should the webhook itself enqueue Brevo events (synchronous insert into `brevo_sync_queue`)? Or should a Postgres trigger on `subscriptions` do it? Trigger-based is safer (covers admin grants, retries, all paths); webhook-based is more controllable but easier to miss edge cases. I recommend trigger.

6. **Language at signup.** The signup form doesn't ask. Options:
   - Capture `x-mioshy-locale` from the request headers in `signupAction()` and write it to `profiles.preferred_language`.
   - Add an explicit "I prefer Hebrew / English" toggle to the form.
   - Both — header gives initial value, user can edit later in account settings.
   - Recommend "both" but confirm.

7. **Unsubscribe scope.** "Unsubscribe from everything" vs "unsubscribe from this specific pillar's marketing". Brevo supports per-list unsubscribe; the schema in §4.4 currently uses a single `unsubscribed_at` flag (global). If per-pillar is needed, the column becomes `unsubscribed_lists jsonb` or a join table.

8. **Pre-launch newsletter signup form.** Not currently present (`/api/leads/upsert` is invoked from internal pricing flows, not from a public "subscribe to the newsletter" widget). Is one in scope for this segmentation rollout?

9. **Existing leads consent audit.** `leads.marketing_consent` exists from `018_leads_consent.sql` and has been collecting `true`/`false` since then. Those rows have no `marketing_consent_at` timestamp. For Brevo upload, do we treat them as opt-ins as-of `created_at`, or back off and treat them as "needs reconfirmation"? GDPR-cautious answer is reconfirmation; pragmatic answer is treat as opt-in with `consent_source='legacy_lead'`. Confirm.

10. **Trigger location for `handle_new_user`-style Brevo enqueue.** The existing `on_auth_user_created` trigger inserts into `profiles`. We could either (a) extend it to also enqueue into `brevo_sync_queue`, or (b) add a separate `AFTER INSERT ON profiles` trigger. (b) is cleaner because admins can backfill profiles without going through `auth.users`.

11. **`BREVO_SENDER_EMAIL` value.** Not in `.env.local` today. What address should Brevo send from — `mioshyoffice@gmail.com` (current contact page email), a domain-verified `hello@mioshy.com`, or something pillar-specific? This is required infrastructure.

12. **Journey-coach-as-sender vs Mioshy-brand-as-sender.** Journey unlock emails today are signed by Itzik as coach. Marketing emails sent through the same Brevo workspace will share suppression/bounce state. Worth thinking about whether marketing should be a separate Brevo sub-account or just a separate `sender` and tag scheme.

## Appendix A — Source observations not surfaced above

- **No `app/api/auth/*` routes.** Auth is entirely via Supabase client SDK + server actions in `app/actions/auth-actions.ts`. There is no custom signup endpoint to hook into.
- **`device_id`** (rate-limit / lead-dedupe key) is generated client-side by `lib/device-id.ts`. It is the only stable identifier for un-authenticated visitors and is used as part of the `(email, device_id)` unique on leads.
- **`subscriptions.email`** is denormalised — it duplicates `auth.users.email`. If the user changes their auth email this column will diverge. Worth knowing for any "send email to subscriber" worker that reads from `subscriptions`.
- **`couple_invitations.invitee_email`** is what we'd use for "invite a partner who isn't a user yet" Brevo contact creation. Today the only email sent at that moment is transactional via `sendBrevoEmail()`; we could also create a Brevo contact at the same time with attribute `partner_pending=true`.
- **The trigger in `002_profiles_auth_hardening.sql` is `SECURITY DEFINER`** and only writes `(id, role)`. A direct extension that tries to write `email` into `profiles` would still need email from `auth.users` (available as `NEW.email` in `auth.users` triggers). Today nothing copies the email down — it's queried via join.
- **`profiles_enforce_role_change()`** trigger blocks non-admin users from elevating themselves. Good to know — admin-only operations like "mark this user as do-not-email" should either bypass via service role or extend allowed columns.
