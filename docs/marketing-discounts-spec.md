## 1. הצורך

לאפשר לאדמין להפעיל **מבצע הנחה** למנויים: כל מי שרוכש מנוי בטווח תאריכים מוגדר מקבל הנחה (ב-% או ב-₪) על **החודש הראשון**. דוגמה: "ביולי — 50% הנחה": כל מי שרוכש מנוי במהלך יולי משלם חצי מחיר בחודש הראשון, ואז חוזר למחיר המלא.

המטרה העסקית: כלי קידום מכירות עצמאי לאדמין, בלי תלות במפתח, להגדלת המרות בקמפיינים (למשל מול תנועת הפייסבוק שכבר רצה).

---

## 2. דרישות — מה האדמין יכול לעשות

עמוד תחת **Marketing** שמאפשר ליצור/לערוך/להפעיל מבצע הנחה עם:

- **טווח תאריכים** (מ-X עד Y) — חלון הזכאות.
- **סוג הנחה:** אחוז (% off) **או** סכום בשקלים (₪ off).
- **ערך ההנחה** (למשל 50% או 20₪).
- **מוצר:** journey / games / הכל (מנויים שבועיים).
- **הפעלה/כיבוי** (`is_active`).
- (אופציונלי) קוד קופון — אך ברירת המחדל **אוטומטי לכל מי שרוכש בטווח** (בלי קוד).

---

## 3. החלטות שננעלו (Itzik, 2026-06-26)

1. **זכאות = לפי תאריך הרכישה** — מי שרוכש מנוי בתוך טווח התאריכים. (לא לפי תאריך הרשמה לאתר.)
2. **סוגי הנחה: אחוז (%) וסכום (₪)** בלבד. (לא "מחיר קבוע לתקופה" בשלב זה.)
3. **משך = החודש הראשון בלבד** — ההנחה חלה על החיובים של החודש הראשון, ואז חזרה למחיר מלא.
4. **מטבע: שקל בלבד ב-v1.** אם יתווסף דולר בעתיד — ערך **עצמאי** משלו (שדה נפרד), **לא** המרה/תלות בשקל. הנחת % ממילא עובדת לשתי המטבעות; הנחת סכום קבוע = ILS בלבד כרגע (לקוח USD לא מקבל את ההנחה הקבועה אם אין לה ערך USD).
5. **אין חפיפת מבצעים — שגיאה.** המערכת **תמנע** יצירה/הפעלה של מבצע שני שיכול להתאים לאותה רכישה (אותו product/all + חלון תאריכים חופף). לא stacking, ואין דו-משמעות — חייב להיות לכל היותר מבצע פעיל תואם אחד.
6. **רצפת סכום (ברירת מחדל — לאישור):** הנחה לעולם לא תוריד את החיוב מתחת למינימום של Cardcom; אם תרד — להצמיד למינימום (clamp). לא ≤0.

## 4. הנקודה הקריטית — "חודש ראשון" על חיוב שבועי

החיוב במיאושי **שבועי** (`lib/billing.ts` — weekly = +7 ימים; cron יומי גובה כל מי שהגיע מועד החיוב, דרך טוקן Cardcom שמור). "חודש ראשון" אינו טבעי בחיוב שבועי, ולכן ממופה כך:

> **"חודש ראשון" = N החיובים השבועיים הראשונים (ברירת מחדל N=4), מוזלים — ואז חזרה למחיר המלא.**

- התשלום הראשון (ה-checkout) מוזל.
- 3 החידושים השבועיים הבאים מוזלים גם הם.
- מהחיוב החמישי ואילך — מחיר מלא.
- `N` ניתן לכוונון (שדה `discounted_charges`, ברירת מחדל 4) כי חודש ≠ בדיוק 4 שבועות.

## 5. מודל נתונים

### 5.1 טבלה חדשה: `subscription_promos`
לא להעמיס על `promotions` הקיימת (היא ל-Adults Buy-X-Get-Y, scope wheel/snakes, וה-percent/amount-off שלה לא מחוברים לכלום).

```
subscription_promos(
  id uuid pk,
  name text,                         -- לתצוגת אדמין ("יולי 50%")
  code text null,                    -- קופון אופציונלי; null = אוטומטי בטווח
  discount_type text,                -- 'percent' | 'fixed_amount'
  percent numeric(5,2) null,         -- ל-percent: 50 (אחוז) — אגנוסטי למטבע
  amount_ils numeric(10,2) null,     -- ל-fixed_amount: 20 (₪)
  amount_usd numeric(10,2) null,     -- ל-fixed_amount: ערך USD עצמאי (v1: null)
  product text,                      -- 'journey' | 'games' | 'all'
  discounted_charges int default 4,  -- "חודש ראשון" = N חיובים
  starts_at timestamptz,             -- חלון הזכאות (לפי תאריך רכישה)
  ends_at   timestamptz,
  is_active boolean default true,
  max_redemptions int null,          -- תקרה כוללת (אופציונלי)
  created_at timestamptz default now()
)
```
RLS: כתיבה לאדמין (service-role), קריאה שרת-side בלבד בזמן checkout.

### 5.2 עמודות חדשות ב-`subscriptions`
כדי לדעת לגבות מוזל ב-N החידושים הראשונים ואז מלא:
- `promo_id uuid null` — המבצע שהוחל.
- `intro_amount numeric(10,2) null` — סכום החיוב המוזל.
- `intro_charges_remaining int default 0` — כמה חידושים מוזלים נותרו.

> `subscriptions.plan_amount` יישאר **המחיר המלא** (כדי שהחידושים אחרי החודש הראשון יהיו מלאים).

## 6. נקודות החיבור (3 — כולן חובה)

1. **checkout (תשלום ראשון)** — `app/api/billing/checkout/create/route.ts` (אחרי `getPlanPrice`, ~שורה 256, לפני ה-insert ל-`checkout_sessions` ולפני `openLowProfile`):
   - בצד השרת בלבד: מצא מבצע פעיל תואם (product + `now` בתוך `starts_at..ends_at` + `is_active`).
   - חשב סכום מוזל (% או ₪), עם רצפה (לא שלילי/אפס — מינימום שמותר ב-Cardcom).
   - כתוב את הסכום המוזל ל-`checkout_sessions.amount`, ושמור גם `promo_id` + `original_amount` (להוסיף עמודות ל-`checkout_sessions`).
   - **אסור לסמוך על הלקוח** — אותו דפוס כמו VAT/cadence.

2. **webhook יצירת מנוי** — `app/api/billing/cardcom/indicator/route.ts` (~שורות 420/455, היכן ש-`plan_amount: session.amount`):
   - `plan_amount` = **`session.original_amount`** (המחיר המלא — כדי שחידושים אחרי החודש הראשון יהיו מלאים).
   - אם יש `promo_id`: כתוב `intro_amount = session.amount` (המוזל), `intro_charges_remaining = discounted_charges − 1` (החיוב הראשון כבר בוצע ב-checkout), `promo_id`.

3. **renewal cron** — `app/api/billing/renewals/run/route.ts` (~שורה 159, היכן ש-`chargeToken({ sumToBill: sub.plan_amount })`):
   - אם `intro_charges_remaining > 0` → גבה `intro_amount`, הפחת ב-1.
   - אחרת → גבה `plan_amount` (מחיר מלא).

## 8. נקודות לשים לב (הוכרעו)

- **USD (הוכרע):** v1 שקל בלבד. הנחת % אגנוסטית למטבע. הנחת סכום: `amount_ils` בלבד כרגע; `amount_usd` שדה עצמאי לעתיד (null = לקוח USD לא מקבל את ההנחה הקבועה). לעולם לא להמיר משקל לדולר.
- **חפיפה (הוכרע):** ולידציה בצד השרת שמונעת שמירת/הפעלת מבצע שני שחלון התאריכים שלו חופף ול-`product` שלו מתנגש (אותו מוצר או 'all') עם מבצע פעיל קיים → **שגיאה ברורה לאדמין**. גם בזמן ה-checkout: לכל היותר מבצע תואם אחד; אם בכל זאת נמצאו שניים — לבחור דטרמיניסטית (האחרון) ולתעד warning.
- **רצפת סכום (ברירת מחדל — לאישור):** clamp למינימום של Cardcom; לעולם לא ≤0.
- **VAT:** המחירים כוללי-מע"מ; ההנחה חלה על הסכום הסופי, והחשבונית מחשבת מע"מ מחדש מהסכום המוזל. לוודא ש-`vat_rate_percent` והחשבונית (uxellent) נגזרים מהסכום המוזל.
- **מבצע ננעל על המנוי:** ההנחה נקבעת ברגע הרכישה ו"ננעלת" דרך `intro_*` — שינוי/כיבוי המבצע בעתיד לא משפיע על מנויים קיימים. הרצוי.
