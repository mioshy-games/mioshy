# הפעלת `BREVO_WEBHOOK_SECRET` — מדריך שלב אחר שלב

**למי זה מיועד:** מי שמבצע את זה בממשקים, בלי לגעת בקוד.
**כמה זמן:** בערך 20 דקות, מזה 10 המתנה בין השלבים.

---

## מה אנחנו מנסים למנוע

הנתיב `https://mioshy.com/api/brevo/unsubscribe-webhook` הוא הכתובת ש-Brevo
פונה אליה כשמישהו לוחץ "הסר אותי מרשימת התפוצה", או כשמייל חוזר כ-hard bounce.
היום **כל אחד באינטרנט** יכול לפנות אליה. אנחנו סוגרים את זה בסוד משותף.

**הסיכון שאתה זיהית, והוא אמיתי:** אם נדרוש את הסוד לפני ש-Brevo יודעת לשלוח
אותו — Brevo תקבל דחייה, **ובקשות הסרה יפסיקו להירשם אצלנו**. אנשים ימשיכו
לקבל דיוור אחרי שביקשו להפסיק. זה חמור יותר מהפרצה.

**הפתרון:** הסדר שלמטה בנוי כך ש-**בשום רגע אין דרישה לסוד ש-Brevo עוד לא
שולחת**. בכל שלב, אם משהו נראה לא טוב, יש חזרה אחורה של דקה.

---

## הדרך שנבחרה: כותרת `Authorization: Bearer` דרך ה-API

סוד בתוך כתובת נכנס ליומני גישה, ל-proxy ולכותרות `Referer` — סתירה ישירה
ל-H5, שזה עתה ניקה סודות מהלוגים. לכן כותרת, לא פרמטר.

Brevo תומכת בזה דרך `auth: {type:"bearer", token:"…"}` בעדכון ה-webhook.
**אין לזה שדה בממשק הגרפי** — רק API. זה שלוש פקודות שמדביקים במסוף.

> ## 🔴 אזהרה קריטית — לקרוא לפני הכל
>
> **הכותרת אינה מופיעה בשום מקום בממשק הגרפי של Brevo.**
>
> מי שיערוך את ה-webhook הזה דרך המסך — אפילו רק כדי לשנות תיאור או לסמן
> אירוע — **עלול למחוק את הכותרת בשקט**, בלי שום אזהרה. התוצאה: הנתיב ידחה
> כל פנייה, **וכל בקשות ההסרה יאבדו**, בלי שאף אחד ישים לב מיד.
>
> **הכלל: את ה-webhook הזה עורכים אך ורק דרך ה-API.**
>
> האזהרה הזו נכתבת גם לתוך שדה ה-`description` של ה-webhook עצמו (פקודה 2),
> כך שמי שיפתח אותו במסך יראה אותה שם.

## שלב 0 — לייצר את הסוד, ולרשום את **אורכו**

צור מחרוזת אקראית של **לפחות 32 תווים**, אותיות וספרות בלבד (בלי רווחים ובלי
סימנים מיוחדים — הם עלולים להישבר בציטוט של המעטפת).

אפשר לייצר כאן: https://www.random.org/strings/ — מחרוזת אחת, עם ספרות
ואותיות, בלי כפילויות.

**שמור אותו בכספת הסיסמאות שלך.**

> ### 📏 רשום גם את מספר התווים של הסוד שלך
>
> פקודה 3 תחזיר שדה `token_len`. הוא צריך להיות **שווה בדיוק לאורך הסוד
> שלך** — כך מוודאים שהוא לא נחתך בהעתקה.
>
> **אין כאן מספר "נכון" קבוע.** לאורך המסמך אכנה את האורך שלך `<N>`.
> *אם הסוד שלך באורך 43 תווים — `<N>` הוא 43, ו-`token_len: 43` הוא הצלחה.*
>
> אם אינך בטוח מה האורך: הדבק את הסוד למונה תווים כלשהו בדפדפן,
> **לא לשורת פקודה** — היא נשמרת בהיסטוריית המעטפת.

בהמשך אכנה את הסוד עצמו `<הסוד>`.

---

### 🔑 שני ערכים שאתה ממלא בעצמך — הם לא עוברים דרכי ולא נכתבים בשום קובץ

| מציין מקום | מה למלא | מאיפה |
|---|---|---|
| `<BREVO_API_KEY>` | מפתח ה-API של Brevo | Brevo → פרופיל (למעלה מימין) → **SMTP & API** → לשונית **API Keys** |
| `<הסוד>` | הסוד שייצרת בשלב 0 | מהכספת שלך |
| `<WEBHOOK_ID>` | מזהה ה-webhook | פלט של פקודה 0 למטה |

**אל תשלח לי אף אחד משלושתם.**

### פקודה 0 — לראות את **כל** ה-webhooks, ולוודא שאתה עורך את הנכון

**אל תניח שיש רק אחד.** אם שני webhooks מצביעים לאותו נתיב ואתה מוסיף כותרת
רק לאחד — השני ימשיך להישלח בלי כותרת, יידחה אחרי המיזוג, **וההסרות שעוברות
דרכו יאבדו** בלי שיהיה ברור למה.

ל-Brevo יש שלושה סוגי webhooks, וכל אחד ברשימה נפרדת. **הרץ את שלושתם:**

```bash
for T in transactional marketing inbound; do
  echo "── $T ──"
  curl -s -X GET "https://api.brevo.com/v3/webhooks?type=$T" \
    -H 'accept: application/json' \
    -H 'api-key: <BREVO_API_KEY>' \
    | jq -r '.webhooks[]? | "\(.id)\t\(.type)\t\(.url)\t\(.description // "")"'
done
```

**בלי `jq`** — הרץ בלי הצינור וקרא את ה-JSON ידנית.

**מה לחפש בפלט:**

| מה רואים | מה זה אומר |
|---|---|
| שורה אחת שהכתובת שלה מכילה `unsubscribe-webhook` | תקין. ה-`id` שלה הוא `<WEBHOOK_ID>` |
| **שתי שורות או יותר** לאותה כתובת | **עצור.** צריך להוסיף כותרת לכולן, או למחוק את המיותרות. **תחזיר לי את הרשימה (בלי מפתח ה-API) לפני שתמשיך.** |
| כתובת שמכילה כבר `?secret=` | מישהו כבר ניסה את מסלול הפרמטר. תגיד לי. |
| אף שורה עם `unsubscribe-webhook` | ה-webhook לא קיים — זה מסביר הרבה. תגיד לי. |

**רשום את `<WEBHOOK_ID>` שבחרת.** אם יש יותר מאחד — חזור עליי, אל תמשיך.

### פקודה 1 — לצלם את ההגדרה הנוכחית (לפני שנוגעים)

```bash
curl -s -X GET 'https://api.brevo.com/v3/webhooks/<WEBHOOK_ID>' \
  -H 'accept: application/json' \
  -H 'api-key: <BREVO_API_KEY>' | jq 'del(.auth.token)'
```

> ### ⚠️ למה `del(.auth.token)` ולמה זה חשוב
>
> **‏Brevo מחזירה את הטוקן במלואו, בלי מיסוך.** אם תדביק את הפלט הגולמי
> ל-`SECURITY-PROGRESS.md`, **תכניס סוד חי לתוך גיט.**
>
> ה-`| jq 'del(.auth.token)'` מוחק אותו לפני שאתה רואה אותו.
> **אם אין לך `jq`** — הרץ בלי הצינור, אבל אז **החלף ידנית** כל ערך
> `"token": "..."` ב-`"token": "<REDACTED>"` לפני ההדבקה.

**את הפלט הזה מדביקים ל-`SECURITY-PROGRESS.md`** — זה ארטיפקט השחזור.
שים לב במיוחד ל-`url`, ל-`events` ול-`description`: **תצטרך אותם בפקודה 2.**

### פקודה 2 — להוסיף את הכותרת

> **למה מעתיקים גם `url` ו-`events`?** כדי לא להסתמך על כך שעדכון חלקי משמר
> שדות שלא נשלחו. אם `events` היה נמחק, ה-webhook היה מפסיק לירות לגמרי.
> העתק אותם **מפלט פקודה 1**, מילה במילה.

```bash
curl -s -X PUT 'https://api.brevo.com/v3/webhooks/<WEBHOOK_ID>' \
  -H 'accept: application/json' \
  -H 'content-type: application/json' \
  -H 'api-key: <BREVO_API_KEY>' \
  -d '{
    "url": "https://mioshy.com/api/brevo/unsubscribe-webhook",
    "description": "mioshy unsubscribe + hard bounce. ⚠️ AUTH HEADER SET VIA API — DO NOT EDIT THIS WEBHOOK IN THE UI, IT WILL SILENTLY DROP THE Authorization HEADER AND ALL UNSUBSCRIBES WILL BE LOST. Edit via API only.",
    "events": ["unsubscribed", "hardBounce"],
    "auth": { "type": "bearer", "token": "<הסוד>" }
  }'
```

**החלף את `events`** ברשימה המדויקת מפלט פקודה 1, אם היא שונה.
**שים לב:** הכתובת כאן **בלי** `?secret=` — הסוד עובר בכותרת.

הפקודה מחזירה **204 בלי גוף**. זה לא אומר שהיא הצליחה — לכן פקודה 3.

---

### פקודה 3 — לאמת שהכותרת באמת נשמרה

**אל תסתמך על התשובה של פקודה 2.** קרא מחדש:

```bash
curl -s -X GET 'https://api.brevo.com/v3/webhooks/<WEBHOOK_ID>' \
  -H 'accept: application/json' \
  -H 'api-key: <BREVO_API_KEY>' \
  | jq '{url, events, auth_type: .auth.type, token_len: (.auth.token // "" | length), token_last4: (.auth.token // "" | .[-4:])}'
```

**מה אמור לחזור:**

```json
{
  "url": "https://mioshy.com/api/brevo/unsubscribe-webhook",
  "events": ["unsubscribed", "hardBounce"],
  "auth_type": "bearer",
  "token_len": <N>,
  "token_last4": "····"
}
```

- `auth_type` = `"bearer"` → הכותרת נשמרה.
- `token_len` = **`<N>`**, האורך שרשמת בשלב 0 → הסוד נכנס במלואו ולא נחתך.
  **זה לא מספר קבוע** — אם הסוד שלך באורך 43, הערך התקין הוא 43.
- `token_last4` → **השווה בעיניים** לארבעת התווים האחרונים בכספת שלך.

הפקודה הזו **לא מדפיסה את הסוד** — רק אורך וארבעה תווים אחרונים. **הפלט
שלה בטוח להדבקה** ל-`SECURITY-PROGRESS.md`.

**אם `auth_type` הוא `null`** — הכותרת לא נשמרה. אל תמשיך לשלב 3. חזור לפקודה 2.

## שלב 4 — הבדיקה, בלי לגעת ברשימת התפוצה

במקום להסיר כתובת אמיתית, מדמים את הבקשה ש-Brevo שולחת. **הבדיקה מתחלקת
לשתיים, והראשונה לא נוגעת בבסיס הנתונים בכלל.**

### 4א — הוכחת הכותרת. **לא משנה שום דבר.**

השתמש בכתובת מייל ש**אין לה חשבון** אצלנו — למשל `probe-<משהו>@example.invalid`.
הנתיב יאמת את הסוד, יחפש את הכתובת, לא ימצא אותה, **ולא יכתוב כלום.**

```bash
curl -s -i -X POST 'https://mioshy.com/api/brevo/unsubscribe-webhook' \
  -H 'content-type: application/json' \
  -H 'authorization: Bearer <הסוד>' \
  -d '{"event":"unsubscribed","email":"<EMAIL>"}'
```

**מה אמור לחזור (הקוד שפרוס כרגע, לפני מיזוג #52):**

| תשובה | מה זה אומר | מה לעשות |
|---|---|---|
| `200` + `{"ok":true,"matched":false}` | **הצלחה.** הסוד התקבל, הכתובת לא קיימת ולכן לא נכתב כלום | המשך ל-4ב |
| `401` + `{"error":"unauthorized"}` | הסוד ב-Brevo/בפקודה שונה מזה שבוורסל | השווה את שניהם. **אל תמשיך** |
| `400` + `{"error":"missing_email"}` | ה-JSON שבור או חסר `email` | בדוק את המרכאות בפקודה |
| `500` | תקלה אצלנו | עצור וקרא לי |

> **למה `matched:false` היא הצלחה:** היא מוכיחה שהבקשה **עברה את בדיקת הסוד**
> והגיעה ללוגיקה. `401` הוא הכישלון, לא `matched:false`.

### 4ב — הוכחת הכתיבה. **משנה שורה אחת, עם ביטול מלא.**

רק אם 4א החזירה `200`. כאן משתמשים בכתובת של **חשבון בדיקה אמיתי** — לא שלך,
ולא של לקוח.

**קודם — צילום המצב הנוכחי, כדי שנוכל להחזיר:**

```sql
SELECT u.email, p.marketing_consent, p.marketing_consent_at, p.marketing_consent_source
  FROM public.profiles p JOIN auth.users u ON u.id = p.id
 WHERE u.email = '<EMAIL>';
```

**שמור את שלושת הערכים.** זה מה שתחזיר בסוף.

עכשיו אותה פקודה מ-4א, עם כתובת חשבון הבדיקה. **התשובה הצפויה:**
`200` + `{"ok":true,"matched":true}` ← `matched:true` הוא ההוכחה שהשורה עודכנה.

**מה השתנה בבסיס הנתונים — שורה אחת בטבלת `profiles`, שלוש עמודות:**

| עמודה | הערך החדש |
|---|---|
| `marketing_consent` | `false` |
| `marketing_consent_at` | הזמן הנוכחי |
| `marketing_consent_source` | `'brevo_unsubscribe'` |

**שום דבר אחר לא נוגע.** לא נמחקות שורות, לא נשלחים מיילים, ו-Brevo עצמה
לא יודעת שהבדיקה קרתה — היא לא מעורבת.

### 4ג — האימות (התשובה עצמה לא מוכיחה שהרישום נכנס)

```sql
SELECT u.email, p.marketing_consent, p.marketing_consent_at, p.marketing_consent_source
  FROM public.profiles p JOIN auth.users u ON u.id = p.id
 WHERE p.marketing_consent_source = 'brevo_unsubscribe'
 ORDER BY p.marketing_consent_at DESC
 LIMIT 5;
```

השורה העליונה צריכה להיות כתובת הבדיקה, `marketing_consent = false`,
וזמן מלפני רגע.

### 4ד — להחזיר את המצב לקדמותו

הצב את שלושת הערכים מהצילום ב-4ב:

```sql
UPDATE public.profiles p
   SET marketing_consent        = <הערך המקורי>,
       marketing_consent_at     = <הערך המקורי או NULL>,
       marketing_consent_source = <הערך המקורי או NULL>
  FROM auth.users u
 WHERE u.id = p.id AND u.email = '<EMAIL>';
```

ואז הרץ שוב את שאילתת הצילום מ-4ב וּודא שהערכים חזרו.

> **אם בטעות שלחת `"event":"hardBounce"`** — זה מוסיף שורה לטבלה אחרת.
> הביטול:
> ```sql
> DELETE FROM public.email_hard_bounces WHERE email = '<EMAIL>';
> ```
> **חשוב:** כל עוד השורה שם, כל שליחה עתידית לכתובת הזו תדולג.

> ### ⏱️ הערה על התזמון
> הטבלה למעלה מתארת את **הקוד שפרוס כרגע**. אחרי מיזוג #52 התשובות הופכות
> אחידות — `{"ok":true}` לכל מקרה, **וגם סוד שגוי יחזיר `200`**. כלומר
> **הבדיקה הזו הכי אינפורמטיבית עכשיו**, לפני המיזוג. אחרי המיזוג ההוכחה
> היחידה היא שאילתת 4ג.

>
> **עד לרגע הזה,** אם היה מתגלה שיבוש היה אפשר פשוט למחוק את המשתנה בוורסל
> והכל היה חוזר לעבוד (הקוד הנוכחי מתעלם מהסוד כשהוא לא מוגדר).
>
> **אחרי המיזוג זה מתהפך:** הקוד החדש **דורש** את הסוד. אם תמחק את המשתנה,
> הנתיב יחזיר שגיאה `503` **לכל** פנייה ו**כל ההסרות יאבדו**.
>
> לכן אחרי שלב 5, התיקון לתקלה הוא **לתקן את הסוד**, לא למחוק אותו.

## שלב 6 — סימני אזהרה, ומה לעשות מיד

### הסימן המרכזי: הסרות מפסיקות להיכנס

הרץ את זה פעם בשבוע, ובוודאות אחרי כל קמפיין דיוור גדול:

### שאילתה ב' — קצב ההסרות לאורך זמן

```sql
SELECT date_trunc('day', p.marketing_consent_at) AS day,
       count(*) AS unsubscribes_recorded
  FROM public.profiles p
 WHERE p.marketing_consent_source = 'brevo_unsubscribe'
   AND p.marketing_consent_at > now() - INTERVAL '30 days'
 GROUP BY 1
 ORDER BY 1 DESC;
```

**מה תקין:** מספרים קטנים אבל לא-אפסיים בימים שבהם יצא דיוור.
**מה מדאיג:** **אפס בימים שבהם יצא דיוור גדול.** זה הסימן המובהק ביותר לכך
שה-webhook נדחה — אנשים לוחצים "הסר", ואנחנו לא שומעים.

### שאילתה ג' — האם hard bounces עדיין נרשמים

```sql
SELECT email, bounced_at, reason, source
  FROM public.email_hard_bounces
 ORDER BY bounced_at DESC
 LIMIT 10;
```

אותו נתיב מטפל גם בהם. אם `bounced_at` העדכני ביותר הוא מלפני שבועות, בעוד
שדיוור יוצא כרגיל — זה אותו כשל.

### הסימן השני: יומן ה-webhook ב-Brevo

באותו מסך שבו הגדרת את ה-webhook, בהיסטוריית השליחות:

| מה רואים | מה זה אומר | מה לעשות |
|---|---|---|
| `200` | הכל תקין | כלום |
| `503` | הסוד לא מוגדר בוורסל, או שהפריסה לא כללה אותו | ודא שהמשתנה קיים ב-Production ובצע Redeploy |
| `200` אבל הסרות לא נרשמות | הסוד ב-Brevo **שונה** מזה שבוורסל | השווה את שניהם תו-בתו. שים לב לרווח בהתחלה או בסוף |
| `404` | הכתובת הודבקה עם שגיאת הקלדה | תקן את הכתובת |

> **למה סוד שגוי מחזיר `200` ולא שגיאה?** זה מכוון. הנתיב מחזיר בדיוק אותה
> תשובה בין אם הסוד נכון או שגוי, כדי שתוקף לא יוכל לנחש. **המשמעות עבורך:
> `200` לבדו אינו הוכחה שזה עובד** — רק שאילתה א' היא ההוכחה.

### הסימן השלישי, והמהיר ביותר: יומן השגיאות של Vercel

מאז המיזוג, **כל דחייה כותבת שורת שגיאה**. זה הופך את הכשל השקט לנראה בלי
שמישהו יצטרך לזכור לבדוק.

Vercel → הפרויקט → **Logs** → חפש:

```
event=rejected scope=brevo.webhook
```

| מה רואים | מה זה אומר |
|---|---|
| אין שורות כאלה | תקין |
| `reason=invalid_secret` | הסוד ב-Brevo שונה מזה שבוורסל — **הסרות נזרקות עכשיו** |
| `reason=not_configured` | המשתנה חסר בוורסל — הנתיב מחזיר 503 לכולם |

השורות האלה נספרות גם ב-error rate של Vercel, כך שאפשר להגדיר עליהן התראה.

### מה לעשות מיד אם הסרות אבדו

1. **אל תמחק את המשתנה בוורסל** (אחרי שלב 5 זה מחמיר את המצב).
2. השווה את הסוד בשני המקומות — Brevo וּוורסל. ברוב המקרים זה רווח מיותר
   או תו שנחתך בהעתקה.
3. תקן את הצד השגוי, בצע Redeploy אם שינית בוורסל, וחזור על שלב 4.
4. אם עדיין לא עובד — קרא לי, ואל תמשיך לנסות. ההסרות שאבדו לא חוזרות
   מעצמן, ונצטרך לייבא אותן מ-Brevo ידנית.

## 🔴 שלושה כללים שנשארים בתוקף אחרי שסיימת

1. **את ה-webhook הזה עורכים רק דרך ה-API.** עריכה במסך תמחק את הכותרת בשקט
   וכל ההסרות ייפסקו. האזהרה כתובה גם בתיאור ה-webhook עצמו.
2. **אחרי המיזוג, לא מוחקים את המשתנה בוורסל.** מחיקה = `503` על כל פנייה.
   התיקון לתקלה הוא לתקן את הסוד.
3. **הסוד מסובב יחד עם שאר הסודות.** הוא יושב בכותרת ולא בכתובת, ולכן אינו
   נכנס ליומני גישה — אבל הוא עדיין סוד.

## אם פקודה נכשלת — מה סביר שתראה

> ### 🔒 אל תדביק לי פלט גולמי ואל תדביק את שורת הפקודה
>
> שורת הפקודה מכילה את **מפתח ה-API**, והפלט של פקודות הקריאה עלול להכיל את
> **הטוקן**. שלח לי רק את **הודעת השגיאה עצמה**, אחרי שהחלפת כל ערך רגיש
> ב-`<REDACTED>`. אם אתה בספק — תאר במילים מה ראית.

| מה תראה | מה זה אומר | מה לעשות |
|---|---|---|
| `{"code":"unauthorized","message":"Key not found"}` | מפתח ה-API שגוי, פג, או הודבק חלקית | צור מפתח חדש ב-Brevo → SMTP & API → API Keys |
| `401` בלי גוף | אותו דבר — לרוב רווח או תו שנחתך בהעתקה | העתק את המפתח מחדש, בלי רווחים בקצוות |
| `{"code":"document_not_found"}` | `<WEBHOOK_ID>` לא קיים | הרץ את פקודה 0 שוב וקח את ה-`id` משם |
| `{"code":"invalid_parameter", ...}` | ה-JSON בפקודה 2 שבור, או ערך `events` לא מוכר | ודא שהעתקת את `events` **בדיוק** מפלט פקודה 1 |
| `403` | למפתח אין הרשאה מתאימה | צור מפתח עם הרשאות מלאות |
| `curl: (3) URL rejected` / `bad range` | בעיית ציטוט של המעטפת — לרוב תו מיוחד בסוד | ודא שהסוד אותיות וספרות בלבד (שלב 0) |
| `jq: command not found` | `jq` לא מותקן | הרץ בלי הצינור `| jq ...` וקרא JSON גולמי — אבל **החלף את הטוקן ידנית** לפני הדבקה |
| **פלט ריק אחרי פקודה 2** | **זו הצלחה.** `PUT` מחזיר 204 בלי גוף | המשך לפקודה 3 — היא ההוכחה היחידה |
| פקודה 3 מחזירה `auth_type: null` | הכותרת לא נשמרה | חזור לפקודה 2. אם נכשל שוב — עצור וקרא לי |
| פקודה 3 מחזירה `token_len` שאינו **`<N>`** | הסוד נחתך בהעתקה. **`<N>` הוא האורך שלך משלב 0** — אם הסוד באורך 43 ו-`token_len` הוא 43, **זו הצלחה** | הרץ את פקודה 2 שוב עם הסוד המלא |

**כלל:** אם משהו נכשל **לפני** שלב 3 (הגדרת המשתנה בוורסל) — שום דבר לא
נשבר בפרודקשן, הקוד עדיין מתעלם מהסוד. יש לך זמן. אל תמהר לתקן בניחוש.
