# הפעלת `BREVO_WEBHOOK_SECRET` — מדריך שלב אחר שלב

**למי זה מיועד:** מי שמבצע את זה בממשקים, בלי לגעת בקוד.
**כמה זמן:** בערך 20 דקות, מזה 10 המתנה בין השלבים.

---

## מה אנחנו מנסים למנוע

הנתיב `https://mioshy.com/api/brevo/unsubscribe-webhook` הוא הכתובת ש-Brevo
פונה אליה כשמישהו לוחץ "הסר אותי מרשימת התפוצה", או כשמייל חוזר כ-hard bounce.
היום **כל אחד באינטרנט** יכול לפנות אליה. אנחנו סוגרים את זה בסוד משותף.

**הסיכון שאתה זיהית, והוא אמיתי:** אם נדרוש את הסוד לפני ש-Brevo יודעת לשלוח
אותו — Brevo תקבל דחייה, **ובקשות הסרה יפסיקו להירשם אצלנו**. אנשים ימשיכו
לקבל דיוור אחרי שביקשו להפסיק. זה חמור יותר מהפרצה.

**הפתרון:** הסדר שלמטה בנוי כך ש-**בשום רגע אין דרישה לסוד ש-Brevo עוד לא
שולחת**. בכל שלב, אם משהו נראה לא טוב, יש חזרה אחורה של דקה.

---

## הדרך שנבחרה: כותרת `Authorization: Bearer` דרך ה-API

סוד בתוך כתובת נכנס ליומני גישה, ל-proxy ולכותרות `Referer` — סתירה ישירה
ל-H5, שזה עתה ניקה סודות מהלוגים. לכן כותרת, לא פרמטר.

Brevo תומכת בזה דרך `auth: {type:"bearer", token:"…"}` בעדכון ה-webhook.
**אין לזה שדה בממשק הגרפי** — רק API. זה שלוש פקודות שמדביקים במסוף.

> ## 🔴 אזהרה קריטית — לקרוא לפני הכל
>
> **הכותרת אינה מופיעה בשום מקום בממשק הגרפי של Brevo.**
>
> מי שיערוך את ה-webhook הזה דרך המסך — אפילו רק כדי לשנות תיאור או לסמן
> אירוע — **עלול למחוק את הכותרת בשקט**, בלי שום אזהרה. התוצאה: הנתיב ידחה
> כל פנייה, **וכל בקשות ההסרה יאבדו**, בלי שאף אחד ישים לב מיד.
>
> **הכלל: את ה-webhook הזה עורכים אך ורק דרך ה-API.**
>
> האזהרה הזו נכתבת גם לתוך שדה ה-`description` של ה-webhook עצמו (פקודה 2),
> כך שמי שיפתח אותו במסך יראה אותה שם.

### 🔑 שני ערכים שאתה ממלא בעצמך — הם לא עוברים דרכי ולא נכתבים בשום קובץ

| מציין מקום | מה למלא | מאיפה |
|---|---|---|
| `<BREVO_API_KEY>` | מפתח ה-API של Brevo | Brevo → פרופיל (למעלה מימין) → **SMTP & API** → לשונית **API Keys** |
| `<הסוד>` | הסוד שייצרת בשלב 0 | מהכספת שלך |
| `<WEBHOOK_ID>` | מזהה ה-webhook | פלט של פקודה 0 למטה |

**אל תשלח לי אף אחד משלושתם.**

### פקודה 0 — למצוא את מזהה ה-webhook

```bash
curl -s -X GET 'https://api.brevo.com/v3/webhooks?type=transactional' \
  -H 'accept: application/json' \
  -H 'api-key: <BREVO_API_KEY>'
```

חפש בפלט את זה ששמו/כתובתו מכילים `unsubscribe-webhook`. קח את ה-`id` שלו.

---

### פקודה 1 — לצלם את ההגדרה הנוכחית (לפני שנוגעים)

```bash
curl -s -X GET 'https://api.brevo.com/v3/webhooks/<WEBHOOK_ID>' \
  -H 'accept: application/json' \
  -H 'api-key: <BREVO_API_KEY>' | jq 'del(.auth.token)'
```

> ### ⚠️ למה `del(.auth.token)` ולמה זה חשוב
>
> **‏Brevo מחזירה את הטוקן במלואו, בלי מיסוך.** אם תדביק את הפלט הגולמי
> ל-`SECURITY-PROGRESS.md`, **תכניס סוד חי לתוך גיט.**
>
> ה-`| jq 'del(.auth.token)'` מוחק אותו לפני שאתה רואה אותו.
> **אם אין לך `jq`** — הרץ בלי הצינור, אבל אז **החלף ידנית** כל ערך
> `"token": "..."` ב-`"token": "<REDACTED>"` לפני ההדבקה.

**את הפלט הזה מדביקים ל-`SECURITY-PROGRESS.md`** — זה ארטיפקט השחזור.
שים לב במיוחד ל-`url`, ל-`events` ול-`description`: **תצטרך אותם בפקודה 2.**

---

### פקודה 2 — להוסיף את הכותרת

> **למה מעתיקים גם `url` ו-`events`?** כדי לא להסתמך על כך שעדכון חלקי משמר
> שדות שלא נשלחו. אם `events` היה נמחק, ה-webhook היה מפסיק לירות לגמרי.
> העתק אותם **מפלט פקודה 1**, מילה במילה.

```bash
curl -s -X PUT 'https://api.brevo.com/v3/webhooks/<WEBHOOK_ID>' \
  -H 'accept: application/json' \
  -H 'content-type: application/json' \
  -H 'api-key: <BREVO_API_KEY>' \
  -d '{
    "url": "https://mioshy.com/api/brevo/unsubscribe-webhook",
    "description": "mioshy unsubscribe + hard bounce. ⚠️ AUTH HEADER SET VIA API — DO NOT EDIT THIS WEBHOOK IN THE UI, IT WILL SILENTLY DROP THE Authorization HEADER AND ALL UNSUBSCRIBES WILL BE LOST. Edit via API only.",
    "events": ["unsubscribed", "hardBounce"],
    "auth": { "type": "bearer", "token": "<הסוד>" }
  }'
```

**החלף את `events`** ברשימה המדויקת מפלט פקודה 1, אם היא שונה.
**שים לב:** הכתובת כאן **בלי** `?secret=` — הסוד עובר בכותרת.

הפקודה מחזירה **204 בלי גוף**. זה לא אומר שהיא הצליחה — לכן פקודה 3.

---

### פקודה 3 — לאמת שהכותרת באמת נשמרה

**אל תסתמך על התשובה של פקודה 2.** קרא מחדש:

```bash
curl -s -X GET 'https://api.brevo.com/v3/webhooks/<WEBHOOK_ID>' \
  -H 'accept: application/json' \
  -H 'api-key: <BREVO_API_KEY>' \
  | jq '{url, events, auth_type: .auth.type, token_len: (.auth.token // "" | length), token_last4: (.auth.token // "" | .[-4:])}'
```

**מה אמור לחזור:**

```json
{
  "url": "https://mioshy.com/api/brevo/unsubscribe-webhook",
  "events": ["unsubscribed", "hardBounce"],
  "auth_type": "bearer",
  "token_len": 40,
  "token_last4": "····"
}
```

- `auth_type` = `"bearer"` → הכותרת נשמרה.
- `token_len` = 40 → הסוד נכנס במלואו (לא נחתך בהעתקה).
- `token_last4` → **השווה בעיניים** לארבעת התווים האחרונים בכספת שלך.

הפקודה הזו **לא מדפיסה את הסוד** — רק אורך וארבעה תווים אחרונים. **הפלט
שלה בטוח להדבקה** ל-`SECURITY-PROGRESS.md`.

**אם `auth_type` הוא `null`** — הכותרת לא נשמרה. אל תמשיך לשלב 3. חזור לפקודה 2.

## שלב 3 — להגדיר את המשתנה בוורסל

**זה השלב שמפעיל את האכיפה בפועל.** מרגע זה הקוד ידרוש את הסוד — ו-Brevo כבר
שולחת אותו מאז שלב 1, כך שאין רגע חסר.

1. היכנס ל-Vercel → הפרויקט **mioshy** → **Settings** → **Environment Variables**.
2. **Add New**:
   - **Name:** `BREVO_WEBHOOK_SECRET`
   - **Value:** `<הסוד>` — בדיוק אותו ערך משלב 1, **בלי** ה-`?secret=`, רק הסוד עצמו.
   - **Environments:** סמן **Production** (ואם יש לך Preview — סמן גם, לא מזיק).
3. שמור.
4. **חשוב:** משתנה חדש נכנס לתוקף רק בפריסה הבאה. לך ל-**Deployments**, מצא את
   הפריסה האחרונה בפרודקשן, ובתפריט השלוש-נקודות בחר **Redeploy**.

**חזרה אחורה, אם משהו נשבר:** מחק את המשתנה ובצע Redeploy. הקוד חוזר להתעלם
מהסוד. **הדרך הזו קיימת רק עד שלב 5 — אחריה היא כבר לא עובדת** (ראה אזהרה שם).

## שלב 4 — הבדיקה האמיתית

זו הבדיקה שסופרת. עכשיו הקוד דורש את הסוד, ו-Brevo אמורה לספק אותו.

**הפעולה:**

1. קח כתובת מייל שיש לה חשבון אצלנו ושאתה שולט בה (למשל כתובת בדיקה שלך).
2. שלח אליה מייל כלשהו מ-Brevo — הכי פשוט: קמפיין בדיקה, או מייל שיווקי קיים.
3. פתח את המייל ולחץ על **קישור ההסרה** שבתחתיתו.
4. המתן דקה.

**השאילתה שמראה שזה נרשם** (Supabase → SQL Editor):

### שאילתה א' — האם ההסרה נרשמה

```sql
SELECT u.email,
       p.marketing_consent,
       p.marketing_consent_at,
       p.marketing_consent_source
  FROM public.profiles p
  JOIN auth.users u ON u.id = p.id
 WHERE p.marketing_consent_source = 'brevo_unsubscribe'
 ORDER BY p.marketing_consent_at DESC
 LIMIT 10;
```

**מה אמור להופיע:** השורה העליונה היא כתובת הבדיקה שלך, עם
`marketing_consent = false`, ו-`marketing_consent_at` מלפני כמה דקות.

**אם השורה שלך לא שם** — משהו לא עובד. עבור לשלב 6.

## שלב 6 — סימני אזהרה, ומה לעשות מיד

### הסימן המרכזי: הסרות מפסיקות להיכנס

הרץ את זה פעם בשבוע, ובוודאות אחרי כל קמפיין דיוור גדול:

### שאילתה ב' — קצב ההסרות לאורך זמן

```sql
SELECT date_trunc('day', p.marketing_consent_at) AS day,
       count(*) AS unsubscribes_recorded
  FROM public.profiles p
 WHERE p.marketing_consent_source = 'brevo_unsubscribe'
   AND p.marketing_consent_at > now() - INTERVAL '30 days'
 GROUP BY 1
 ORDER BY 1 DESC;
```

**מה תקין:** מספרים קטנים אבל לא-אפסיים בימים שבהם יצא דיוור.
**מה מדאיג:** **אפס בימים שבהם יצא דיוור גדול.** זה הסימן המובהק ביותר לכך
שה-webhook נדחה — אנשים לוחצים "הסר", ואנחנו לא שומעים.

### שאילתה ג' — האם hard bounces עדיין נרשמים

```sql
SELECT email, bounced_at, reason, source
  FROM public.email_hard_bounces
 ORDER BY bounced_at DESC
 LIMIT 10;
```

אותו נתיב מטפל גם בהם. אם `bounced_at` העדכני ביותר הוא מלפני שבועות, בעוד
שדיוור יוצא כרגיל — זה אותו כשל.

### הסימן השני: יומן ה-webhook ב-Brevo

באותו מסך שבו הגדרת את ה-webhook, בהיסטוריית השליחות:

| מה רואים | מה זה אומר | מה לעשות |
|---|---|---|
| `200` | הכל תקין | כלום |
| `503` | הסוד לא מוגדר בוורסל, או שהפריסה לא כללה אותו | ודא שהמשתנה קיים ב-Production ובצע Redeploy |
| `200` אבל הסרות לא נרשמות | הסוד ב-Brevo **שונה** מזה שבוורסל | השווה את שניהם תו-בתו. שים לב לרווח בהתחלה או בסוף |
| `404` | הכתובת הודבקה עם שגיאת הקלדה | תקן את הכתובת |

> **למה סוד שגוי מחזיר `200` ולא שגיאה?** זה מכוון. הנתיב מחזיר בדיוק אותה
> תשובה בין אם הסוד נכון או שגוי, כדי שתוקף לא יוכל לנחש. **המשמעות עבורך:
> `200` לבדו אינו הוכחה שזה עובד** — רק שאילתה א' היא ההוכחה.

### הסימן השלישי, והמהיר ביותר: יומן השגיאות של Vercel

מאז המיזוג, **כל דחייה כותבת שורת שגיאה**. זה הופך את הכשל השקט לנראה בלי
שמישהו יצטרך לזכור לבדוק.

Vercel → הפרויקט → **Logs** → חפש:

```
event=rejected scope=brevo.webhook
```

| מה רואים | מה זה אומר |
|---|---|
| אין שורות כאלה | תקין |
| `reason=invalid_secret` | הסוד ב-Brevo שונה מזה שבוורסל — **הסרות נזרקות עכשיו** |
| `reason=not_configured` | המשתנה חסר בוורסל — הנתיב מחזיר 503 לכולם |

השורות האלה נספרות גם ב-error rate של Vercel, כך שאפשר להגדיר עליהן התראה.

### מה לעשות מיד אם הסרות אבדו

1. **אל תמחק את המשתנה בוורסל** (אחרי שלב 5 זה מחמיר את המצב).
2. השווה את הסוד בשני המקומות — Brevo וּוורסל. ברוב המקרים זה רווח מיותר
   או תו שנחתך בהעתקה.
3. תקן את הצד השגוי, בצע Redeploy אם שינית בוורסל, וחזור על שלב 4.
4. אם עדיין לא עובד — קרא לי, ואל תמשיך לנסות. ההסרות שאבדו לא חוזרות
   מעצמן, ונצטרך לייבא אותן מ-Brevo ידנית.

## 🔴 שלושה כללים שנשארים בתוקף אחרי שסיימת

1. **את ה-webhook הזה עורכים רק דרך ה-API.** עריכה במסך תמחק את הכותרת בשקט
   וכל ההסרות ייפסקו. האזהרה כתובה גם בתיאור ה-webhook עצמו.
2. **אחרי המיזוג, לא מוחקים את המשתנה בוורסל.** מחיקה = `503` על כל פנייה.
   התיקון לתקלה הוא לתקן את הסוד.
3. **הסוד מסובב יחד עם שאר הסודות.** הוא יושב בכותרת ולא בכתובת, ולכן אינו
